# Learnings

- 2026-09-07 — Planning: `ose-public` already ships `apps/rhino-cli` under the same acronym — RHINO, Repository Hygiene & INtegration Orchestrator — with an overlapping command surface and a `repo-config.yml` declaring `schema: rhino-cli/repo-config/v1`. It has already travelled Go → Rust → F#. The standalone repository is therefore not a new name but a third implementation of an existing identity, which is why this plan aligns command spelling and schema shape rather than inventing them.
- 2026-09-07 — Planning: Badakmini's repository-specific surface is small and enumerable — roughly a dozen constants across `Governance.fs` and `HarnessContract.fs`. The port is large, but the generalization is not: it is one configuration file, not an abstraction layer.
- 2026-09-07 — Planning: Rust's `tests/` directory links only against a crate's library target, so the library-plus-binary split is a requirement of the chosen test layout rather than a stylistic preference. A bin-only crate would have forced the behaviour corpus into `#[cfg(test)]` modules inside `src/`, which is precisely the boundary this repository's BDD standard forbids.
- 2026-09-07 — Planning: HIPPO builds every release asset in one Ubuntu job because Go cross-compiles to Darwin. Rust does not without an Apple SDK, so the release pipeline necessarily becomes a native build matrix feeding one publishing job. This is the one place where following HIPPO exactly would have produced a design that cannot work.
- 2026-09-07 — Planning: `beaver-nest.sln` contains only Badakmini projects and two solution folders, so the cutover removes .NET from this repository entirely rather than merely shrinking its footprint. The `setup-dotnet` step in the scheduled gates goes with it.
- 2026-09-07 — Planning risk accepted: the proof strategy is the shared scenario corpus at three adapter levels, not a byte-for-byte differential run. 81 scenarios cover roughly 5,000 lines of F#, so a behaviour no scenario covers can change silently. The compensating controls are the injected-violation check during cutover — which proves "clean" means "checked" — and one narrow numeric exception comparing word counts file by file, because that gate's output is an integer and a Unicode word-boundary difference would move files across a threshold without failing any scenario.
- 2026-09-07 — Planning decision: the `md links validate` leaf is renamed `md internal-link validate`. Both Badakmini and `ose-public` use the shorter name, and both mislead — the validator resolves local document targets and never fetches or reports on an external URL, so a maintainer reading `[links]` in a gate log could reasonably believe external links are covered. Naming the promise correctly was judged more valuable than matching a spelling a future merge can adopt in a single rename. The configuration section follows the same path (`md-internal-link`), which is also where the general rule came from: an owned section is named after the command that reads it, exactly as `ose-public`'s `governance-word-budget` already is.
- 2026-09-07 — Dependency decision, YAML: selected `yaml_serde` (`github.com/yaml/yaml-serde`), the YAML organization's own continuation of the archived `serde_yaml`. Evidence: last push 2026-08-18, `0.10.7` published 2026-08-18, seven releases during 2026, multiple human maintainers including Ingy döt Net, active Dependabot, 1.63M recent downloads, and no OSV or RustSec advisory against it or its `libyaml-rs` parser. Rejected `noyalib` despite its pure-Rust zero-`unsafe` pitch, because it is published by the author of `serde_yml` and `libyml` — RUSTSEC-2025-0068 and RUSTSEC-2025-0067, both unsound and archived — and sits at `0.0.39` with ten releases in six days; the dependency-selection test of a credible defect-response path is precisely what that history fails. `serde_norway` and `serde_yaml_ng` are held as fallbacks. Noted caveat: `libyaml-rs` is c2rust-transpiled C, so roughly 11k lines of `unsafe` sit below our `#![forbid(unsafe_code)]` crate; `cargo deny check` is the control.
- 2026-09-07 — Documentation model: adopted HIPPO's wholesale rather than inventing one, because it is the same maintainer's answer to the same problem — a standalone tool consumed by repositories that did not write it. The parts that carry weight are not the emoji headings but the two truth rules: `specs/` is canonical and `docs/` may not contradict it, and no command or transcript is published that has not been executed against the current build. One deliberate addition HIPPO cannot make: RHINO is itself the documentation validator, so it ships its own `repo-config.yml` and CI runs the freshly built binary against its own tree — a second real corpus on every push, and proof the schema describes a repository other than BeaverNest before any sibling adopts it.
- 2026-09-07 — Hooks: HIPPO and BeaverNest already run the same skeleton — `pre-commit` to `lint-staged`, `commit-msg` to `commitlint`, `pre-push` to the quick gate — so RHINO adopts it rather than inventing a third. One deliberate divergence: HIPPO's pre-push is unguarded because HIPPO cannot depend on HIPPO, a bootstrapping constraint RHINO does not share, so RHINO guards its pre-push the way BeaverNest does. Shell formatting is not adopted, because `shfmt` is free in Go's toolchain and absent from Rust's, and the upstream shell surface is three two-line hooks. On the consumer side the opposite conclusion holds: `./rhino` is a 547-line security-critical script BeaverNest owns rather than vendors, so it earns `shellcheck` — correctness, not style.
- 2026-09-07 — Plan restructure: RHINO becomes its own first consumer, before the release tag and before BeaverNest. The corpus cannot find inherited assumptions, because the scenarios were written by the same person holding them; a second real repository can. RHINO's tree is the most usefully different one available — no governance tree, no plans tree, two mapped trees instead of four, and an empty harness roster that forces an answer to a question the schema would otherwise defer, namely that an omitted section is an error while a genuinely empty roster is an explicit declaration. Ordering it before the tag matters because a published tag is never replaced.
- 2026-09-07 — Test boundaries: adopted BeaverNest's canonical definitions from the quality-gate standard rather than HIPPO's arrangement, and doing so caught a real defect in an earlier draft of this plan. That draft copied HIPPO's `test-quick.sh`, which runs all three behaviour adapters in pre-push; BeaverNest forbids integration and E2E scenarios in `test:quick` and in every Git hook, and routes them to a scheduled gate instead. HIPPO can do it because it is a single self-hosting module with no scheduled split. Two boundary rules do the real work for a CLI: classify by the strongest real boundary touched by setup, subject, or assertions; and E2E is defined by public-boundary observation, not by permission to use more resources — spawning a child process is explicitly an integration affordance, so what makes RHINO's E2E adapter E2E is that it observes only the process contract. Cargo compiles `tests/<name>/main.rs` as one target, so BeaverNest's separate-directories rule and Rust's convention turn out to be the same layout. Also preserved: the no-loopback policy test is a product invariant stricter than the integration layer, which permits an owned loopback socket — Badakmini's README says so explicitly, and without that note someone would eventually relax it to the layer rule.
- 2026-09-07 — Scope change to four consumers, and two discoveries that justified it. First: grind-in-public already runs `apps/badakmini-cli`, but written independently in **Go** as `badak-mini`, whose own README says the name means "rhinoceros" in Indonesian and that its grammar follows a slice of `ose-public`'s `rhino-cli`. The same validator has therefore been written three times in three languages — `rhino-cli` (Go, then Rust, now F#), Badakmini (F#), `badak-mini` (Go) — which states the case for extraction as history rather than prediction, and makes grind-in-public a second retirement cutover rather than an additive install. Second: HIPPO has no `CLAUDE.md` and no harness adapter directories at all, a degenerate case beyond RHINO's empty roster, which forces `instruction-adapter` to become optional while the competing-instruction-source prohibition stays in full force.
- 2026-09-07 — Generalization detail worth not losing: grind-in-public and HIPPO use ASCII art rather than Mermaid, so both contain zero diagrams. That is a policy difference, not an absence — BeaverNest's visualization convention mandates Mermaid and grind-in-public's does not. The tool must report an explicit clean zero and never warn, or a repository with a different visualization convention becomes a second-class consumer. It also means zero must be distinguishable from a directory walk that silently found nothing, which is a real defect class the BeaverNest-only corpus would never have surfaced.

- 2026-09-07 — Three porting hazards the inventory surfaced that are not about unsupported syntax, and would otherwise have been found by a failing scenario rather than by reading. First, `$` differs: .NET's `$` matches before a trailing `\n` at the end of input, Rust's does not — patterns 6, 9, 15, 22, 24, and 26 anchor on `$` and must either be applied to already-split lines or use `(?m)` deliberately. Second, pattern 29's lookahead is doing real work — it terminates the `[mcp_servers.nx-mcp]` body at the next TOML table header or end of input — so the rewrite is a line-wise section scanner, not a cleverer regex; that is a better implementation regardless of engine, because a TOML table body is a structure and not a text span. Third, pattern 2's lookbehind exists only to exclude image syntax `![alt](src)`, which in explicit parsing is a one-character check on the byte preceding the `[` — the rewrite is smaller than the pattern it replaces. None of the three rewrites is a workaround; each removes a regex that was carrying structure it should not have been carrying.

- 2026-09-07 — Dependency decision, regex engine (AC-02), the remaining open item. **Need:** 31 patterns, 28 of which port unchanged; the tool reads repository-controlled Markdown, so pattern-matching runs over content the tool does not author. **Decision:** the `regex` crate at `1.13.1`, with the three unsupported patterns rewritten as explicit parsing per the inventory. **Evidence:** OSV reports RUSTSEC-2022-0013 / GHSA-m5pq-gvj9-9vr8 against `regex`, fixed in 1.5.5 and therefore not applicable at 1.13.x; `cargo deny check advisories` is the standing control rather than this one-time reading. **Rejected alternatives:** `fancy-regex` would have made all 31 patterns port verbatim by adding lookaround and backreferences, and was rejected precisely because that is what it does — it falls back to backtracking for those constructs, so a repository could commit Markdown that makes the gate hang, and the linear-time guarantee is the reason `regex` is the right engine for a tool pointed at content it does not control. `pcre2` was rejected for the same reason plus a C dependency, which contradicts both `#![forbid(unsafe_code)]` and the binary-size ceiling. Hand-rolled parsing throughout was rejected as unjustified: 28 patterns port cleanly and rewriting them would be work with no decision attached. **Ownership impact:** three hand-written parsers to maintain — an image-prefix check, a TOML table-body scanner, and line splitting — all of which are smaller and more legible than the patterns they replace, so the ownership cost is negative rather than positive.

The binding registry and the step vocabulary were clean on the first pass in all three reviews: 108 scenarios bound exactly once at each adapter, no orphan binding, no scenario written in a sentence outside the vocabulary. The generic-tool rule was clean of the failure it was written for — no `750`, no `repo-governance`, no harness named in an assertion — which matters, because the failures were all the _opposite_ shape.

- 2026-09-07 — What the failures had in common, and why the count is the wrong summary. Thirty-one of the forty-six were one parser defect, not thirty-one bad scenarios. Of the fifteen real ones, thirteen were the same species: **a scenario asserting a policy value that nothing had declared**. The de-policying pass removed BeaverNest's constants from the assertions and, in thirteen places, forgot to put a declaration back in the arrangement. `directory-map` planted an 800-word file to prove the map validator ignores word-budget concerns — but with no surface declared, 800 words violates nothing, so there was nothing to ignore and the scenario could not fail for its stated reason. The `800` was BeaverNest's `751` with the limit deleted and the number left behind. All seven `internal-link` scenarios established no configuration at all, and RHINO exits `2` when it cannot read one, so scenarios asserting `0` or `1` were unreachable rather than merely thin. The generalizable lesson: **removing a hard-coded policy from an assertion is only half the change; the other half is declaring it in the arrangement, and nothing mechanical catches the missing half.** An exact search for the literal passes either way.

- 2026-09-07 — Three defects in the test harness's own parser, and the reason they were invisible (AC-03). The hand-written Gherkin reader was written to serve the static coverage check and the three adapters from one parse. It shipped with three faults, each of which silently changed what scenarios asserted.
  1. **Escaped pipes were column separators.** The CLI corpus writes an argument vector as `governance\|word-budget\|validate` in a one-column table; the reader split on every `|`, so 31 expanded rows invoked the token `governance\` and threw the rest away. Half failed loudly. The other half — the rows asserting exit `2` — **passed**, because a truncated command is also an invalid one. Twelve rows were green while invoking nothing they named.
  2. **`Background:` was discarded.** Four features declare their policy there. Every scenario in them was asserting against policy nothing had established — the exact failure the reword existed to remove, reintroduced by the harness rather than the corpus.
  3. **Docstrings were discarded, and `#` opened a comment inside them.** A fixture whose first line is a Markdown heading vanished with the file it described, so every content-inspecting scenario inspected an empty tree.

  None was catchable by reading the corpus, and none would have been caught by a green run, because at RED everything fails anyway and at GREEN they would have shifted the goalposts rather than broken. They were found by a reviewer compiling the repository's own reader and running it over the corpus instead of reading the feature files by eye. **The method lesson: a hand-written parser in the test harness is production code and needs its own tests before the corpus it parses is trusted.** Five now exist in the quick gate. Two are specific; three are general, and the general one worth keeping is that a step sentence ending in a colon must arrive carrying a table, a bullet list, or a docstring — a promised payload that arrives empty is the shape all three defects took, so it generalises past the three that were found.

- 2026-09-07 — Harness parity, and what a mutation-run review found that a green run did not (AC-02, AC-03, Phase 3).

**Disposition 29 is closed, and closing it removed a pattern rather than porting one.** The predecessor terminated a TOML table body with a lookahead — a pattern that has to know the file's own syntax to find the end of a section. RHINO parses instead: `serde_json` for JSON, the `toml` crate for TOML, both into one `serde_json::Value`, and then a recursive search for an object entry **named** after the required server that carries a command and arguments. No vendor key (`mcpServers`, `mcp_servers`, or anything a fourth harness invents) appears anywhere in `src/`. The comparison that results is about the executable vector rather than about text, which is what the corpus asked for and what a lookahead could never have given. Two regexes now remain in the whole of `src/`, both in Markdown link parsing.

**The mandated Gherkin implementation review rejected the first implementation. Seventeen of twenty mutants survived it.** That number is the useful one, and it is worth stating why counting green scenarios would not have found any of them: every one of the 22 harness-parity scenarios passed.

The single worst finding was not about harness parity at all. The sentence `the repository snapshot is unchanged` read `world.snapshot`, which a previous step had set to `world.files.clone()`. Nothing between them wrote to `world.files`. The assertion compared the harness with the harness and **could not fail at any boundary**. A validator that wrote a file into the repository it was inspecting passed everywhere. `AGENTS.md` states that read-only inspection is enforced by tests; it was enforced by nothing.

Everything else was one defect with several faces. **A fixture that breaks two or three rules at once, asserted against a kind that several rules share, proves none of them.** Three examples, each confirmed by deleting the rule and watching the scenario pass:

| Scenario as written                                | What it broke                               | What survived deleting                                     |
| -------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------- |
| Skill descriptions and routes cannot drift         | description **and** body, in one wrapper    | the description rule, the body rule, and the name rule     |
| Malformed or duplicated canonical skills fail      | one directory whose name matched no rule    | three of the four `invalid-skill` rules                    |
| Extra agent prompt content or semantic drift fails | prompt in one adapter, semantics in another | exchanging the two labels, so every finding is mislabelled |

The repair is structural rather than a list of stronger assertions. `Driver::invoke` now returns a `Run` carrying what the adapter observed on **both sides** of the invocation, walked with `std::fs` rather than through the port — because the claim is that nothing was written, not that nothing the validator can see was written. Every multi-fault fixture is split so one scenario breaks one rule. Every production arm has its own message. Every assertion names the path as well as the rule, through a new sentence `the harness-parity violation for {string} is {string}`. Eight branches the corpus proved nowhere — both missing instruction sources, digest scoping, capability arguments, an absent capability file, the constraint vocabulary, the per-harness command directory, the sealed file's name — gained scenarios of their own. The corpus went from 109 scenarios and 200 expanded to **120 and 211**, and all eleven additions are consequences of this review.

**A rule was deleted rather than tested, because it could not run.** Duplicate canonical skills were detected by keying a map on the declared name — but the declared name is required to equal its own directory, and directories are unique, so the collision branch was unreachable. Requiring the two to match makes duplication _unrepresentable_ rather than merely detectable, which is the stronger property. The branch is gone and the corpus says what is actually enforced. Worth remembering as a shape: a test that cannot be written for a branch is sometimes a signal that the branch is dead, not that the test is hard.

**One asymmetry is stated rather than hidden.** Nineteen of the twenty mutants die at all three boundaries. The twentieth — a validator writing into the tree — dies at **E2E only**. At unit and integration `rhino::execute` runs inside the test process, so a write to a hard-coded relative path lands in the crate root rather than in the sandbox, and whichever scenario ran first would have created it before the read-only scenario looked. Only at E2E is the inspected repository also the process's working directory. The unit and integration rows still read genuine before-and-after evidence; they prove less, and `tests/support/world.rs` says so at the observation itself so a future reader does not mistake a backstop for a proof.

**Four harness defects the review found outside the feature**, all fixed: `reseed_contract` left behind the files a previous contract shape owned, so a repository could hold both a `.json` and a `.toml` capability declaration for one harness; `steps::dispatch` was dead code returning `Unimplemented` for every sentence while the real dispatcher lived elsewhere; the exemption forbidden-word check scanned only the boundary field, so "too slow for CI" would have passed in the alternative-proof field; and `Report::inspected_one` carried a doc line describing a different method.

## The CLI contract: a flag that changes which repository is read is the one to distrust

_2026-09-07, Phase 3, `efc6b6a` and `053edb1`._

The second mandated Gherkin implementation review ran over 195 rows and found one production defect worth the whole exercise. **`--root` inherited the caller's scan exclusions.** The tool read `repo-config.yml` from the working directory, applied that file's `scan.exclude-directories` to the tree, and only then rerooted — so a repository selected with `--root` was walked with a stranger's exclusion list. Reproduced end to end: cwd excluding `guides`, `--root` pointed at a repository that excludes nothing and holds a failing diagram, and the tool answered `checked 0 diagrams, no findings` with exit `0` where the control answered exit `1`.

That is a false clean produced by the one flag whose entire purpose is to change which repository gets read, and it is the failure this tool exists to prevent. The shape is worth naming: **configuration read before the subject is chosen belongs to the wrong subject.** The fix gives `Tree` an `excluding` seam, removes the pre-emptive exclusion from the process entry point, applies exclusions only after the selected repository's own configuration is loaded, and makes a reroot deliberately not carry the previous root's list across.

Three lesser defects fell out of the same review. `--file /rules/README.md` was silently reinterpreted as repository-relative while `--directory` was checked, so one of two sibling flags inspected a file the caller did not name. `--json` silently overrode an explicit `--output text`, which made the same two flags mean different things depending on the order a script assembled them. And `--help` short-circuits before flag validation — left as-is, because answering a help request is not a policy decision, but it now has a row of its own so the behaviour is written down rather than discovered.

**The corpus was the larger failure, and it failed in one recognisable way: sixty-three rows asserted an exit code and nothing else.** Exit `0` is the single least discriminating observation a CLI makes, because it is what _correct_ looks like and also what _did nothing_ looks like.

| Rows | What they asserted | What would have passed                        |
| ---- | ------------------ | --------------------------------------------- |
| 48   | help exits 0       | a build printing an empty help body           |
| 9    | flags exit 0       | a build turning `--quiet` into a help request |
| 3    | `--root` exits 0   | a `--root` that ignores its argument entirely |
| 3    | validators exit 0  | a validator that walks nothing                |

The last row is the general case of a lesson this plan has now learned twice: **a clean walk of nothing and a clean walk of something produce the same exit code**, so a fixture with nothing in it can only prove that the tool did not crash. The nothing-to-find fixture now carries a resolvable link and an accessible diagram for exactly that reason, and the scenarios assert the counts.

The `--root` row is a subtler instance and worth its own note. Every `--root` scenario pointed the flag at the tree the run would have used anyway, so the flag was exercised without ever being _load-bearing_ — the prefix-stripping body of `MemoryTree::rooted_at` was executed by no scenario in the corpus. A flag has to be pointed somewhere the default would not have gone before its scenario means anything.

**Proof: eleven mutants, all killed.** Nine die at all three boundaries. The remaining two are a matched pair, and their boundary-specificity is structural rather than an omission: `MemoryTree::rooted_at` is reachable only from unit and `DiskTree::rooted_at` only from integration and E2E, so a mutant of either can only die where that tree is in use. Together they cover `--root` at every boundary — which is a different claim from "one mutant survives somewhere", and the difference is worth stating rather than glossing.

**Harness hygiene, third occurrence of the same species.** Three JSON readers in the test support were substring scanners: `json_number` could answer a question about the run with a member of the same name from inside a violation, `json_string` truncated at the first `"` and so silently cut every message containing an escaped quote, and `first_violation` split on the first `}` and so ended a record early whenever a message contained one. All three now parse structurally. A test harness that reads its subject's output with weaker machinery than the subject wrote it with can hide the subject's bugs behind its own.
