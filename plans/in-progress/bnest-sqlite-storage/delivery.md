# Delivery

All product work remains pending until execution is explicitly underway. Each checkbox is independently verifiable; a failed phase checkpoint blocks later phases.

Every phase applies [live-service continuity](../../../repo-governance/development/live-service-continuity.md): Bnest stays routed throughout, the sole backend is never stopped, Tailscale is never repointed for a normal release, only one release slot may write at a time, and no compatible client is required to refresh. A failed active-route health check stops all other work until the route is restored.

- [x] `[AI] [AC-05] [AC-08]` Input: overlap and rollback constraints. Action: implement bounded final-write gate, atomic phase pointer, compatibility mirror or transactional outbox, pending-parity health, and rollback guard. Outcome: acknowledged writes cannot silently make a retained rollback reader stale. Proof: fault injection before/after primary commit, concurrent old/new writers, mirror retry, restart, and rollback eligibility tests. **Decision (2026-08-29, user-confirmed):** the atomic phase pointer (`Config.write!/1`, temp-file + rename) and pre-activation verification gate are implemented and tested, but no live dual-write/outbox exists — `StorageCoordinator.active_backend/1` routes every write to exactly one backend. The flat-file mirror is therefore a **point-in-time snapshot taken at migration**, not a continuously-current rollback target: rollback is safe as the _code revision_ before cutover, or by restoring the snapshot, but flipping the phase pointer back to `flat_primary` sometime after cutover would read stale data for anything written to SQLite since. This was an open question in this plan's own `learnings.md` from planning, resolved by explicit user decision rather than left unimplemented by oversight. No further build work follows from this item.
