# Learnings

## Capture Rule

Record only safe facts: source revision, target name, port role, pass/fail, duration, aggregate process resource values, and anonymous synthetic-journey outcome. Do not record machine paths, hostnames, Tailscale identity, credentials, cookies, keys, user names, user records, request payloads, or logs containing them.

## Observations

- **2026-08-27 — Repository release baseline.** `bnest-app` exposes `proxy:install`, `proxy:status`, `release:build`, `deploy:prepare`, `deploy:promote`, `deploy:rollback`, and `deploy:retire` through Nx. Its deployment script starts the candidate with LaunchAgents, checks `/health/ready` plus `X-Bnest-Revision`, and switches Caddy through a graceful reload. Disposition: retained in [technical documentation](tech-docs.md#current-condition).
- **2026-08-27 — Runtime observation unavailable in this shell.** `proxy:status` stopped before it could inspect Caddy because `BNEST_DEPLOY_ROOT` was not set. This is expected secret-safe configuration validation, not evidence of outage. Disposition: defer actual baseline collection to Delivery Phase 1 with an authorized machine-local environment.
- **2026-08-27 — Prior art found.** [Zero-downtime local rollouts](../../ideas/q1-urgent-important/zero-downtime-local-rollouts.md) predicted the need for an immutable candidate, a stable proxy, rollback, and bounded cleanup. Disposition: the formal plan records the now-implemented baseline; no duplicate idea is created.
- **2026-08-27 — Primary documentation checked.** Official LiveView guidance confirms automatic reconnect but warns that process state can be lost; Caddy documents graceful reload and delayed stream closure; Tailscale documents direct reverse proxying but not health-gated drain/promotion; Mix does not provide hot upgrades out of the box; Nx cache correctness depends on complete deterministic inputs. Disposition: sources and resulting corrections are integrated into [technical documentation](tech-docs.md#primary-source-verification).
- **2026-08-27 — Deterministic AI operation requested.** The release should run fixed tests before creating an artifact and minimize routine AI context. Disposition: `[AC-04]` and the [deterministic release constraints](tech-docs.md#deterministic-release-constraints) require a revision-bound, fail-closed state machine and bounded structured summaries.
- **2026-08-27 — Recommendation requested.** The plan must choose a preferred solution rather than only list alternatives. Disposition: [ephemeral blue/green Caddy with one deterministic release transaction](tech-docs.md#recommendation-and-ranking) is recommended; direct single-slot Tailscale is conditional on measured benefit and complete recovery proof.
- **2026-08-27 — Automatic recovery is not yet covered.** The canonical deployment-reconnect browser step calls `page.reload()`. It proves persistence across a reload, not automatic LiveView/WebSocket recovery, in-progress input preservation, or absence of duplicate actions. Disposition: Phase 1 requires a checked-in no-reload scenario before any live measurement.
- **2026-08-27 — Rollback has warm and cold forms.** `deploy:rollback` promotes the recorded previous slot only while it remains prepared. After `deploy:retire`, the retained artifact must be re-prepared and revision-checked before promotion. Disposition: both recovery edges are explicit in technical documentation and delivery.
- **2026-08-27 — Production cannot be the authenticated test data root.** Repository rules require synthetic identities and records to live under a marked, isolated test run and forbid testing through real sessions or production records. Disposition: Phase 1 must design and prove an isolated served verification surface; absent that proof, authenticated live-route measurement is blocked rather than weakened.
- **2026-08-27 — Rendered release labels were visibly clipped.** The supplied release-state screenshot shows transition text cut off even though the diagram remained renderable. Disposition: `[AC-06]`, the [Mermaid legibility prerequisite](tech-docs.md#mermaid-legibility-prerequisite), and a deferred delivery task define a deterministic Badakmini/pre-push guard; no validator or hook code changes in this documentation-only iteration.

Repository, specification, implementation, and official-source claims reconcile; active-service, rollback, test-isolation, Mermaid-enforcement, and human-authorization boundaries are explicit. Disposition: Phase 1 assessment may proceed only when requested. Product/release and Badakmini/pre-push implementation remain blocked by the plan status, pending evidence, exact specification/file impact, and human authorization.
