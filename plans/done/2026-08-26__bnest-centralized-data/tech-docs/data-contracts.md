# Data Contracts

This companion to [technical documentation](README.md) defines the proposed version-1 runtime records. Examples contain synthetic placeholders only. Implementation must encode UTF-8 JSON, reject unknown required values, validate before use, and atomically replace mutable records.

## Root and Path Rules

Every path below is relative to one startup-resolved `<runtime-root>`:

```text
<runtime-root>/
├── general/
├── apps/beaver-nest/
│   └── legacy/<import-id>/source.bin
├── system/
│   ├── bootstrap.json
│   ├── accounts/<user-id>.json
│   ├── usernames/<normalized-username>.json
│   ├── sessions/<session-record-id>.json
│   ├── manifests/<import-id>.json
│   └── schema-registry.json
└── users/<user-id>/
    ├── legacy/<import-id>/source.bin
    ├── imports/<import-id>.json
    ├── chat/current.json
    ├── sifat-allah/progress.json
    └── preferences/theme.json
```

Production resolves `<runtime-root>` to `data/prod/`; one filesystem test resolves it to `data/test/runs/<run-id>/`. The server generates every ID. Browser input may choose only an allow-listed source type, never a path, ID, owner, or schema version.

## Shared Field Rules

- `schemaVersion` is a positive integer owned by the record type.
- IDs are URL-safe random identifiers generated by the server; examples use readable placeholders.
- Timestamps are UTC RFC 3339 strings generated by the server.
- SHA-256 values are lowercase 64-character hexadecimal digests over documented bytes.
- Readers reject missing required fields, wrong types, unsupported versions, invalid enums, and extra security-sensitive fields.
- Mutable records use one per-path lock, write a sibling temporary file, flush it, atomically replace the destination, and re-read it.
- Mutable user records start at `revision: 0`; writes require the last-read revision and increment it. A mismatch returns `stale` without replacing data.
- Immutable envelopes, legacy recovery copies, and accepted manifests are never overwritten. A retry either returns the accepted identity or creates a new attempt linked to it.

## Identity Records

### Bootstrap marker

Path: `system/bootstrap.json`. It journals the only bootstrap attempt so a process crash cannot leave ambiguous partial accounts.

```json
{
  "schemaVersion": 1,
  "recordType": "bootstrap",
  "state": "closed",
  "attemptId": "bootstrap-synthetic-001",
  "startedAt": "2030-01-01T00:00:00Z",
  "closedAt": "2030-01-01T00:00:00Z",
  "accounts": [
    {
      "userId": "user-synthetic-admin",
      "normalizedUsername": "familyadmin",
      "accountSha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
      "indexSha256": "dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd"
    }
  ]
}
```

`state` is `pending` or `closed`. A pending record has `closedAt: null`; it is written before account files and lists the exact server-generated IDs and expected checksums. Startup under the same global lock either completes matching files or removes only files whose ID/checksum matches that attempt, then returns to setup. `accounts` is non-empty and must include an `admin`. Once state is `closed`, setup never reopens automatically.

### Account

Path: `system/accounts/<user-id>.json`.

```json
{
  "schemaVersion": 1,
  "recordType": "account",
  "userId": "user-synthetic-admin",
  "displayUsername": "FamilyAdmin",
  "normalizedUsername": "familyadmin",
  "roles": ["parents", "admin"],
  "passwordVerifier": "$argon2id$v=19$m=32768,t=2,p=1$synthetic-salt$synthetic-hash",
  "createdAt": "2030-01-01T00:00:00Z"
}
```

`roles` is a non-empty unique subset of `children`, `parents`, and `admin`. `normalizedUsername` follows the 1–32 character policy in [technical documentation](README.md#username-and-password). `passwordVerifier` must parse as an encoded Argon2id verifier; [OWASP password-storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) supplies the selected minimum. The verifier is sensitive runtime material and is excluded from logs, audit output, production-derived fixtures, and committed evidence.

### Username index

Path: `system/usernames/<normalized-username>.json`.

```json
{
  "schemaVersion": 1,
  "recordType": "username-index",
  "normalizedUsername": "familyadmin",
  "userId": "user-synthetic-admin"
}
```

The normalized value must equal the filename stem and the linked account value. Setup acquires one global identity-store lock, rejects an existing index, then writes the account and index as one recoverable transaction.

### Browser session

Path: `system/sessions/<session-record-id>.json` where `<session-record-id>` is the lowercase SHA-256 digest of the opaque cookie token.

```json
{
  "schemaVersion": 1,
  "recordType": "browser-session",
  "tokenDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "userId": "user-synthetic-admin",
  "issuedAt": "2030-01-01T00:00:00Z",
  "revokedAt": null
}
```

`tokenDigest` must equal the filename stem. `revokedAt` is null or a timestamp not earlier than `issuedAt`. There is deliberately no server-expiry field. Logout atomically sets `revokedAt` for only the presented digest and broadcasts that digest's LiveView disconnect; it does not scan or revoke sibling browser sessions.

## User Records

### Immutable browser-import envelope

Path: `users/<user-id>/imports/<import-id>.json`.

```json
{
  "schemaVersion": 1,
  "recordType": "browser-import",
  "importId": "import-synthetic-001",
  "ownerId": "user-synthetic-child",
  "source": {
    "kind": "browser-storage",
    "storageArea": "sessionStorage",
    "storageKey": "bnest.chat.v1",
    "sourceSchemaVersion": 2
  },
  "payloadEncoding": "utf8-string",
  "payload": "{\"version\":2,\"thread_id\":null,\"model\":\"fixture-model\",\"reasoning_effort\":\"medium\",\"messages\":[]}",
  "integrity": {
    "sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
    "capturedAt": "2030-01-01T00:00:00Z"
  }
}
```

The checksum covers the exact UTF-8 bytes of `payload`. The source combination must be one of:

- `sessionStorage` and `bnest.chat.v1`;
- `localStorage` and `bnest.sifat-allah.v1`; or
- `localStorage` and `phx:theme`.

The envelope is written before normalization and never edited. Import outcome belongs in the manifest so an interrupted attempt cannot corrupt its source evidence.

### Central chat

Path: `users/<user-id>/chat/current.json`.

```json
{
  "schemaVersion": 1,
  "recordType": "chat",
  "ownerId": "user-synthetic-child",
  "sourceImportId": "import-synthetic-001",
  "revision": 0,
  "state": {
    "version": 2,
    "thread_id": null,
    "model": "fixture-model",
    "reasoning_effort": "medium",
    "messages": []
  },
  "updatedAt": "2030-01-01T00:00:01Z"
}
```

`sourceImportId` is the accepted envelope ID or null for a chat first created centrally. `revision` is a non-negative integer used for compare-and-swap writes. `state` obeys the existing version-2 `BnestApp.Chat` snapshot contract: at most 200 alternating visitor/assistant messages; sequential positive IDs; content at most 100,000 bytes; model at most 128 bytes; optional thread ID at most 512 bytes; and an allowed reasoning effort. Transient `busy`, streaming, and UI error state are never stored.

### Central Sifat Allah progress

Path: `users/<user-id>/sifat-allah/progress.json`.

```json
{
  "schemaVersion": 1,
  "recordType": "sifat-allah-progress",
  "ownerId": "user-synthetic-child",
  "sourceImportId": "import-synthetic-002",
  "revision": 0,
  "progress": {
    "version": 2,
    "learned_ids": [],
    "review_ids": [],
    "mastered_key_ids": [],
    "review_key_ids": [],
    "correct_answers": 0,
    "incorrect_answers": 0
  },
  "session": null,
  "updatedAt": "2030-01-01T00:00:01Z"
}
```

ID lists must contain only IDs accepted by `BnestApp.SifatAllah`; answer counts are non-negative integers. `session` is one of the exact shapes below. Question `kind` is one of `wajib_meaning`, `wajib_opposite`, `mustahil_meaning`, `meaning_wajib`, `mustahil_opposite`, or `meaning_mustahil`; imported aliases `meaning`, `opposite`, and `opposite_meaning` normalize to the first three. `feedback` is null or `remembered` for study, and null, `success`, or `retry` for quiz/review.

```json
{"mode":"dashboard"}
{"mode":"study","lesson_ids":["wujud"],"lesson_index":0,"feedback":null}
{"mode":"quiz","quiz_pair_id":"wujud","quiz_kind":"wajib_meaning","quiz_scope":"all","feedback":null}
{"mode":"review","review_pair_id":"wujud","review_kind":"wajib_meaning","feedback":null}
```

Study IDs are non-empty, unique curriculum IDs and the index is in range. Quiz scope is `all` or `learned`; pair/kind must exist and learned scope must point to a mastered key unless feedback is present. Review pair/kind must exist. Invalid optional session state falls back to dashboard without discarding valid progress. The full encoded browser source remains limited to 10,000 bytes during import.

### Theme preference

Path: `users/<user-id>/preferences/theme.json`.

```json
{
  "schemaVersion": 1,
  "recordType": "theme-preference",
  "ownerId": "user-synthetic-child",
  "sourceImportId": "import-synthetic-003",
  "revision": 0,
  "theme": "dark",
  "updatedAt": "2030-01-01T00:00:01Z"
}
```

`theme` is `light` or `dark`; `revision` uses the same compare-and-swap rule as chat and learning. An absent `phx:theme` means system theme: record that absence in the manifest and do not create this file. Removing an explicit preference deletes this mutable record only with the expected revision after the UI confirms system theme; it never deletes its import envelope.

## Migration Records

### Import manifest

Path: `system/manifests/<import-id>.json`.

```json
{
  "schemaVersion": 1,
  "recordType": "import-manifest",
  "importId": "import-synthetic-001",
  "ownerId": "user-synthetic-child",
  "source": {
    "kind": "browser-storage",
    "reference": "bnest.chat.v1",
    "sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"
  },
  "destination": {
    "recordType": "chat",
    "relativePathTemplate": "users/<owner-id>/chat/current.json"
  },
  "recoverySource": {
    "kind": "import-envelope",
    "relativePathTemplate": "users/<owner-id>/imports/<import-id>.json#payload",
    "sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"
  },
  "status": "accepted",
  "attempt": 1,
  "startedAt": "2030-01-01T00:00:00Z",
  "completedAt": "2030-01-01T00:00:01Z",
  "failureCategory": null
}
```

`ownerId` is a stable user ID for user/browser imports or null for shared/system legacy sources. `status` is `pending`, `retryable`, `rejected`, or `accepted`. `failureCategory` is null for pending/accepted or one safe enum such as `unsupported-version`, `oversized`, `malformed`, `owner-unresolved`, `stale-revision`, `write-failed`, or `read-back-failed`. Runtime records resolve templates internally; logs and schema-audit output never reveal identity-bearing concrete paths.

The idempotency key is the tuple of owner ID/namespace, source kind/reference, and source checksum. A retry of an accepted tuple returns the accepted result. A retryable attempt increments `attempt` under the manifest lock without overwriting its recovery source.

### Recovery source bytes

For a browser import, the immutable envelope's exact UTF-8 `payload` is the recovery source; creating a second raw backup would add no safety. For a legacy file, `apps/beaver-nest/legacy/<import-id>/source.bin` or `users/<user-id>/legacy/<import-id>/source.bin` is the immutable byte-for-byte copy. The manifest states the source type, checksum, destination type, and lifecycle. Restore verifies recovery-source bytes before parsing or writing a candidate.

### Schema registry

Path: `system/schema-registry.json`.

```json
{
  "schemaVersion": 1,
  "recordType": "schema-registry",
  "supported": {
    "bootstrap": [1],
    "account": [1],
    "username-index": [1],
    "browser-session": [1],
    "browser-import": [1],
    "chat": [1],
    "sifat-allah-progress": [1],
    "theme-preference": [1],
    "import-manifest": [1],
    "schema-registry": [1]
  },
  "migrations": [
    {
      "recordType": "chat-source",
      "from": 1,
      "to": 2,
      "migrationId": "chat-source-v1-to-v2"
    },
    {
      "recordType": "sifat-allah-source",
      "from": 1,
      "to": 2,
      "migrationId": "sifat-source-v1-to-v2"
    }
  ]
}
```

The registry declares support; code remains the validator. A new schema version adds a reader and pure migration before any writer emits it. Old readers remain during the compatibility window defined in [migration design](migration-design.md).

## Test-run Marker

Path: `<runtime-root>/.bnest-test-run.json`, present only when `<runtime-root>` is `data/test/runs/<run-id>/`.

```json
{
  "schemaVersion": 1,
  "recordType": "bnest-test-run",
  "runId": "run-synthetic-001",
  "createdAt": "2030-01-01T00:00:00Z",
  "owner": "bnest-test-harness"
}
```

The marker `runId` must equal the directory name. Cleanup re-resolves the path, rejects symlinks and paths outside `data/test/runs/`, validates this marker, confirms the application and browsers stopped, then removes only the exact run directory.

## Source Compatibility

| Source                  | Accepted current form                                            | Target behavior                                                                                      |
| ----------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Chat version 1          | `thread_id`, messages; current 500,000-byte connect limit.       | Purely add default model/reasoning, validate as current chat version 2, retain raw envelope.         |
| Chat version 2          | Current `BnestApp.Chat` snapshot.                                | Validate and wrap as central chat record without altering transcript/thread values.                  |
| Sifat Allah version 1   | Legacy learned/review IDs or legacy key IDs.                     | Use existing pure version-1 restore, emit validated version-2 progress, retain raw envelope.         |
| Sifat Allah version 2   | Current progress plus optional valid session; 10,000-byte limit. | Validate, separate progress/session fields, and retain raw envelope.                                 |
| `phx:theme`             | `light`, `dark`, or absent.                                      | Write explicit preference for light/dark; record absence without a preference file.                  |
| Unknown/malformed input | Any other key, type, version, or oversized payload.              | Preserve client source, record safe rejected/retryable outcome, do not change accepted central data. |

## Schema Evolution

For every future schema change:

1. Document old and new shapes, defaults, removed fields, and compatibility window.
2. Add a reader and pure migration from every supported old version.
3. Preserve and checksum an immutable recovery source before producing a candidate.
4. Write and re-read the candidate through the normal repository operation.
5. Mark acceptance only after schema and checksum proof; otherwise keep the old active record.
6. Remove an old reader only in a later archival plan after restore rehearsal.

## Production Schema Audit Projection

The read-only schema audit reduces a record to public structure before comparison:

```json
{
  "recordType": "chat",
  "schemaVersion": 1,
  "fields": {
    "ownerId": "string",
    "recordType": "string",
    "revision": "integer",
    "schemaVersion": "integer",
    "sourceImportId": "string-or-null",
    "state": "object",
    "updatedAt": "string"
  }
}
```

It emits only record type/version and mismatch category. It must not emit record counts, concrete paths, IDs, usernames, hashes, verifiers, session material, nested payload fields, or values; authenticate as a user; copy production into tests; or write, normalize, migrate, lock, repair, or delete anything.
